A green test suite tells you the tests ran, not that they'd catch a regression. witness flips one operator per line of your source — >→>=, &&→|| — and reruns your own tests. A mutant that survives is a line your suite can't tell from a bug: test-theatre. The pass is an un-forgeable, re-runnable Proof-of-Play receipt. No LLM, zero dependencies.

In plain words. witness checks your tests, not your code. It makes small deliberate mistakes in your code, one at a time — a "greater than" becomes "greater than or equal", an "and" becomes an "or" — and runs your tests after each one. If your tests still pass with the mistake in, they would not have noticed that bug either, and witness names the exact line.

Then it writes a short receipt: which files, which tests, how many mistakes were caught, under exactly which version of the gate, sealed with a hash. Anyone can run the same check and get the same hash. A receipt copied onto code it does not describe is refused.

Start here

Six steps from nothing to a gate in your pull requests. You need a repository whose tests run from one command and exit non-zero when a test fails.

  1. Pick the files where a wrong comparison costs money or trust — validators, pricing, permission checks, parsers. Start with two or three; you can add more later.
  2. Time your tests once. witness runs them once per mutant, and it refuses a per-mutant bound under …× an honest run, because a bound that is too tight makes every mutant time out and count as caught.
  3. Commit one file, witness.bench.json, at the root of the repository: 
    { "files": ["src/pricing.js", "src/auth.js"],
  "testCommand": "npm test" }
  4. Add one step to your workflow (pin the exact tag — the receipt fingerprints the gate, so a moving tag would move your anchor): 
    - uses: actions/checkout@v4
- run: npm ci
- name: witness — proof of play
  uses: sjgant80-hub/witness@v0.7
  5. Open the run. The step summary lists every surviving line as file:line — the flip — the code, and the run keeps witness-receipt.json, witness-verdict.json and a badge as the witness-proof artifact.
  6. Close each survivor. Usually the fix is a test, not a code change: add the case that pins that boundary (for n > 0, test 0). If no test can ever tell the two apart — an equivalent mutant — record it in witness.baseline.json with a reason of at least … characters. It is matched to the exact line, so it stops applying the moment that line changes.

Prefer to try it on your laptop first? The gate is two files; nothing is installed.

# ⚑ not `npx witness` — that npm name belongs to an unrelated package
git clone --depth 1 --branch v0.7 https://github.com/sjgant80-hub/witness.git .witness
node .witness/witness.mjs mutate src/pricing.js --test npm test
node .witness/witness.mjs fuzz src/parse.js parseOrder        # hostile input must never throw
node .witness/witness-bench.mjs prove . > receipt.json       # mint the receipt
PROOF_ASSESSOR=.witness/witness-bench.mjs \
  node .witness/vendor/proof-of-play/filter.mjs verify receipt.json "$PWD"   ✓ AUTHENTIC

How it works

The flow below is the code, in order, with the numbers filled in from the real vercel/ms receipt (landing/ms-verdict.json).

Step by step, in the code

  1. commentMask() scans the source — it does not regex it — and marks comment bytes. An operator in a comment can never be killed by a test, so it is not offered. Strings are left mutable on purpose: a changed error message or pattern really does change the program.
  2. mutants() finds each spaced operator ( > , not >, so => and >>> are never hit) and makes one copy of the file per site with exactly that one flip.
  3. runMutations() runs your suite once, unmutated. A red baseline would make every mutant look caught, so it refuses. It times that run and refuses a bound under …× it.
  4. Before touching your file it writes an atomic backup beside it; if a run is ever killed half way, the next run heals from it. Each mutant is written, your tests run under runner.mjs, and the original is restored in a finally.
  5. A mutant the tests fail on (or time out on) is killed. A mutant they pass is a survivor, unless witness.baseline.json holds an argued reason for that exact line.
  6. witness-bench.mjs turns the per-file counts into a verdict and hashes it, together with a fingerprint of witness itself, into the anchor. The receipt carries the anchor. The vendored proof-of-play verify re-runs the gate and compares.

Why the receipt can't be faked

Authenticity rests on a reproducible hash, not a signer. verify re-runs the benchmark and tells the refusals apart instead of calling everyone a forger: benchmark-changed (the gate moved — an instrument fingerprint is baked into the proof), verdict-changed (your code or tests moved — re-prove), anchor-mismatch (the forgery shape), and repo-mismatch (a receipt carried to another repository). The gate is turned on itself: every organ below is mutation-gated in this repo's own CI.

Adoption

What it does for a team. Code review asks "is this change right?". Nobody has time to ask the second question on every pull request: "would our tests have caught it if it were wrong?". witness asks that second question mechanically, on the lines you choose, every time — and it matters most where the tests were written by the same hand as the code, including an AI assistant's hand. A pull request whose new tests do not actually guard its new behaviour gets a red check that names the line.

  1. One repository, report only. Add the step to your riskiest repository with continue-on-error: true on it. Read the survivors for a sprint; they are a map of where your suite is thinner than it looks.
  2. Close or argue every survivor. Add the missing boundary tests; record genuine equivalents in witness.baseline.json with their reasons. Review those reasons like code — they are the only way a survivor goes quiet.
  3. Make it required. Remove continue-on-error and add the check to branch protection. From here a change that weakens a guarded line cannot merge quietly.
  4. Grow the list. Add files to witness.bench.json as they earn it. For a suite too slow to run per pull request, run the gate nightly with cap set, and keep the per-PR gate on the core files.
  5. Keep the receipts. Each run's witness-proof artifact is a reproducible record of test effectiveness for that commit. An auditor, a customer or another team re-runs verify and gets the same anchor — or a refusal that says why.

    Risks, answered straight

    It runs our tests many times. Is it slow?

    Yes, by design: one run of your suite for the baseline and one per mutant, so a gate takes roughly (mutants + 1) × your suite time. Mutants run one at a time, because each one changes a file in your working copy; your suite may still run its own tests in parallel inside each run. To split a long gate, give separate CI jobs separate files, as this repository's own CI does. Gate the behaviour-critical files, set cap, and run a large suite nightly rather than per pull request. witness refuses a bound that is too tight instead of quietly scoring every timeout as a catch.

    What if our tests are flaky?

    Then the gate is as flaky as they are. A test that fails at random can make a mutant look caught when it was the flake that failed. witness only refuses a baseline that is red on its single honest run; it cannot see a flake that happened to pass. Gate the files whose tests are deterministic first, and treat a survivor that comes and goes between runs as a flaky test to fix.

    Some survivors can never be killed.

    True — equivalent mutants are a known floor of mutation testing. They go in witness.baseline.json with an argued reason; each is tied to the exact line and lapses when that line changes. This repo's own gate carries its exemptions in public, each with its reason.

    Does a clean gate mean our code is correct?

    No. It means your tests notice each of the … kinds of one-operator change at every site in the files you named. That is a strong, specific statement about the tests — not a proof that the code meets its requirements.

    Which languages?

    It is built for JavaScript and TypeScript-style sources: the comment masker understands that syntax (comments, strings, templates, regexes). The test command can be anything that exits non-zero on failure.

    It runs code. Is that safe?

    It runs your own test command on your own runner — what CI already does. The optional verify server refuses unknown repositories unless it is deployed in a disposable container, and says so rather than pretending.

    Who else uses it?

    No outside team has it in their CI yet. The proof so far is the landing above: the gate run on a widely used external library, reproduced on GitHub's runner, receipt committed. You would be among the first; the MIT licence means that carries no lock-in risk.

    What if the supplier disappears?

    Nothing changes. Two files, MIT, pinned by tag, no service behind them.

    White paper

    The problem: green is not guarded

    A passing suite proves the tests ran. It does not prove they would fail if the code were wrong. The common shape is a suite for isPositive that checks 1 and -1 but never 0; the day someone writes n >= 0, every test still passes. Coverage does not see this — the line was executed. Review rarely sees it — the test looks fine. We call it test-theatre, and audits of our own code kept finding it, along with functions documented as tolerant that crash on hostile input.

    The method: mutation testing, made deterministic

    Mutation testing is an old, well-studied idea (DeMillo, Lipton and Sayward, Hints on Test Data Selection, IEEE Computer, 1978): change the program slightly and see whether the tests notice. witness keeps it small and strict — … spaced operator flips, one per mutant, so a survivor names one line — and makes it deterministic: the same source, deterministic tests and the same gate give the same verdict on any machine.

    What the gate refuses to do

    Most of witness is refusals, each one a real failure it once produced. It will not score a file with nothing to mutate as clean. It will not gate a red baseline, which would make every mutant look caught. It will not accept a per-mutant bound under …× the honest run, which would let timeouts score a perfect result. It will not offer a mutant inside a comment, which no test could ever kill. It will not let an exemption through without a reason, and it says out loud when it refuses one. It will not leave orphaned processes or a mutated file behind. And since v0.7 it will not exit silently when run through a symlink, and a stray quote cannot hide the next line of code from it.

    The receipt: a claim anyone can re-run

    The verdict — badge, counts, the spec and a fingerprint of the gate itself — is serialised canonically and hashed. The receipt carries that anchor. Verification does not trust a signature; it re-runs the gate and compares. A changed gate, a changed result, a fabricated anchor and a receipt moved to another repository are each refused, and named as what they are.

    Evidence and limits

    The landing above is the external evidence: a widely used library, its own tests, two honest survivors at unguarded boundaries, reproduced on GitHub's runner. The internal evidence is the blueprint: every organ of witness is gated by witness in CI, with the receipts on this page checked against the files. The limits are stated in the risks above: a clean gate is a statement about the tests, for these operators, in these files — not a proof of correctness.

    The lesson it caught in itself

    witness spawns your test runner. The first time it ran under its own node --test suite, every mutant falsely "survived" — the child inherited NODE_TEST_CONTEXT and exited 0 even on failure. A hard kill mid-run once baked a live mutant into a fixture. Both are designed out now: the child env is scrubbed and the gate self-heals from a sidecar after any interrupt. A build gate has to be hardened against the exact bug classes it hunts.
